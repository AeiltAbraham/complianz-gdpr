# Learnings

Lessons and scored instincts captured by `/flow:learn` and `/flow:retro`.

### 2026-10-06 flow gate hook matches the command text, not what actually runs
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: The PreToolUse gate (flow `scripts/gate.js`) regex-matches the raw Bash command string. During `/flow:init`, a self-test whose JSON payload merely contained `git commit --no-verify` inside quotes was blocked before anything ran. The commit regex (`\bgit(\s+\S+)*\s+commit\b`) also spans chained commands, so any command with `git …` followed later by a space-separated `commit` or `push` word triggers the full check run first.
action: Keep the words `git … commit` / `git … push` and the skip-hooks flag out of any Bash command that is not a real commit or push. Put such text (test payloads, snippets) in a file with the Write tool and reference the file instead.
promote-at: 0.8 -> becomes a CLAUDE.md line, or a gate.js fix proposed upstream via `/flow:retro` (match executed commands, not quoted text)

### 2026-10-07 don't set a verification bar that normal e2e flake can't clear
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: For T-010 (visual/isolation screenshot baselines) the dispatcher demanded "5x double-proof all green + repeat-each + throttle" — 12+ cold runs, each perfect. Against a suite with ~1/10 residual flake (a login-cookie race + one banner screen at 768px), any single flake fails the campaign, so the implementer looped regenerate->fail->restart for ~4.5h without converging. The plan's own policy (§8.1.4) was the right bar all along: green with CI retries (`retries: 2`), anything that only passes on retry flagged flaky. After taking over, fixing the real login race (retry + nav wait) and seeding the documents the banner preview needs, the suite went 3x clean with retries unused.
action: When accepting an inherently flaky e2e/screenshot suite, use the project's retry policy (green with retries, flaky flagged) as the bar, not "N cold runs all green". Fix the identifiable root-cause flakes (races, missing deterministic state) directly; let retries absorb irreducible transient flake. Watch for an agent thrashing (repeated full re-runs, same ~1 failure each pass) as the signal the bar is wrong, and intervene rather than wait.
promote-at: 0.8 -> becomes a line in the planning or tdd skill: proof commands for flaky suites specify the retry policy, never a perfect-cold-run count

### 2026-10-08 verify e2e on a RESET db, one pass per task
confidence: 0.5   # raised: the "same-DB, many runs" habit hid a real CI-blocking bug AND burned hours
context: The screenshot baselines (T-010) and a page-rules assertion passed every verification for three tasks (T-010, T-011, T-032) but only because every run reused the same ACCUMULATED wp-env DB. A `npx wp-env reset` (fresh DB = the real CI condition) exposed that the seed does not pin Complianz's notices/notifications, so those screens/assertions were non-reproducible and would have failed in CI. Separately, running two or three full fresh-DB verifications per task (each ~15 min: reset → reseed → build → suite) turned the baseline work into hours the maintainer pushed back on.
action: Verify e2e work on a RESET database (`npx wp-env reset` first), never the accumulated one — "passes locally" must equal "passes in CI". And run ONE fresh-DB verification pass per task, not a stack of them; trust the agent's own logged fresh-DB runs plus a read of the raw log over re-running. Accept flaky-then-passes under the agreed `--retries=2` policy; don't open a determinism hunt for every retry-absorbed flake.
promote-at: 0.8 -> a line in conventions.md "Gate"/testing section and the flow planning skill (e2e proofs reset the DB; one verify pass)

### 2026-10-10 don't key CSS tokens to a DOM element a later phase will create
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: tokens.css (T-020) declared the `--cmplz-*` semantic tokens ONLY on `#complianz-app-root[data-cmplz-ui], #complianz-portal-root[data-cmplz-ui]`, but `#complianz-app-root` is not rendered until the Phase-5 marker move (ADR-001) — the app mounts into `#complianz-app` and Page.js's root is `.cmplz-wrapper`, neither carrying the id/marker. The portal root DOES exist, so portal content (dialogs/popovers/combobox menu) was fine, masking the gap. Every MAIN-APP primitive consumer (T-026 Support textarea, T-027 combobox control, T-028's 7 inputs) therefore resolved every `var(--cmplz-*)` to invalid-at-computed-value-time -> token-less render (dark currentColor border, 0 radius, 0 inline padding, no focus ring). It slipped three tasks because the primitives were unused until T-026+, functional e2e doesn't assert styling, and visual.spec is non-blocking (Option B) against stale baselines, so the drift never hard-failed; the T-028 implementer misread the 26-screen drift as a minor text-color shift. The adversarial review surfaced it but the verify step wrongly dismissed it as "accepted Phase-2 state" (it misread ADR-001's deferral of the marker MOVE as a deferral of working tokens). Caught by manually confirming the CSS source + fresh build + reading the visual.spec actual.png (a dark square NumberInput).
action: Scope design tokens to the SAME selector model as the scoped base (base.css targets `[data-cmplz-ui] *`; tokens now declare on `:is(#complianz,#complianz-portal) :where([data-cmplz-ui])`) so they reach every migrated island in the phase they are consumed, not a root element a future phase introduces. When a token/base layer and its consumers land in different tasks, VISUALLY verify one real consumer renders look-preserving in the running app (read the screenshot), don't trust functional-green + non-blocking visual drift. And when an adversarial-review verify step dismisses a finding as "accepted/known", re-check the primary evidence before trusting it.
promote-at: 0.8 -> a line in ADR-001/ADR-014 (token scope = island model until Phase 5) and the conventions "look-preserving means verify a rendered consumer" note

### 2026-10-11 never put the data-cmplz-ui marker on a container that wraps UNMIGRATED bodies
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-038 (Phase-3 shell) put `data-cmplz-ui` on the `.cmplz-content-area .cmplz-grid` CONTAINER to give the frame its tokens. But that container WRAPS the still-legacy Phase-4 screen bodies, so the scoped base reset (base.css B1–B5, selector `:is(#complianz,#complianz-portal) :where([data-cmplz-ui] *)`, specificity (1,0,0) from the `:is(#id)`) then reached every legacy `<button>`/`<input>`/inline-svg under it. (1,0,0) beats ALL class-based legacy admin CSS (≤(0,N,0)), so B4/B3/B1 stripped real buttons to transparent/borderless/dark-text, B1 stripped raw input borders, and B5 `height:auto` ballooned a height-only info SVG — across nearly every screen, with NO tw- utilities to restore them (those elements aren't migrated). The three green specs missed it: fields=functional, smoke=renders, isolation=no-leak-OUTSIDE-#complianz; none assert in-grid content styling. The island model only works when the marker sits on a FULLY-migrated subtree (leaf primitives self-mark, so `[data-cmplz-ui] *` only hits their own tw--restored internals). Caught by the adversarial review (flow:reviewer) + confirmed by reading the regenerated tools-data screenshot.
action: Put `data-cmplz-ui` ONLY on fully-migrated subtrees (migrated leaf components self-mark; Header/Menu when they migrate). NEVER on a container that still wraps unmigrated bodies — the base reset will strip their legacy styling with nothing to restore. A frame that wraps unmigrated content gets its redesign via tw- utilities (scoped by the `important: :is(#complianz,#complianz-portal)` config, NOT the marker) + tokens referenced with a literal fallback (`var(--cmplz-space-l,24px)`) so they resolve now and auto-upgrade when the Phase-5 marker move lands on the app root. This is exactly why ADR-001 defers the marker move to Phase 5 (all bodies migrated). For shell/Phase-4 tasks, verify by reading a screenshot of an UNMIGRATED screen with buttons/inputs — functional-green won't catch the leak.
promote-at: 0.8 -> a line in ADR-001 (marker only on fully-migrated subtrees; container markers wait for Phase 5) and the planning/shell-migration guidance

### 2026-10-12 migrating field/body chrome: global legacy rules, transient animations, and tint-text AA
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-045 (Phase-4 section 1, wizard field-row chrome) — the pre-push adversarial review (5-dimension workflow, each finding verified) caught three defects a single migrator pass missed, all generalizable to the remaining Phase-4 body sections. (1) GLOBAL legacy rules: fields.scss carried `#complianz .cmplz-error-text` and `#complianz .cmplz-comment` at the TOP level (not under `div[class^="cmplz-wizard-"]`), so they styled NON-Field consumers too (AceEditorControl, CreateProcessingAgreements, Service, PlaceholderPreview). The migrator deleted them as "reproduced in JS" — orphaning those consumers (ADR-005 violation + visual regression). (2) Transient animation → static bg: the legacy save-highlight was a one-shot `animation: fadeIt 3s` that faded OUT; the migrator replaced it with a static `tw-bg-[--cmplz-success-surface]` keyed on `highLightField===field.id`, but that store value is never reset, so the row stayed green permanently. (3) Tint-text AA: `--cmplz-accent-strong` (#1e73be) text on the `--cmplz-accent-subtle` (#e3f2ff) tint is only 4.33:1 — below WCAG AA for ~11px text (constitution §5), and the axe gate can't catch it (no wizard screen in MIGRATED_SCREENS). The maintainer-approved preview had certified only BODY text on the tints, never accent-strong-on-tint, so the sign-off was not an informed AA waiver of that element.
action: When migrating body chrome, (1) grep every legacy class the deleted SCSS styled for consumers OUTSIDE the migrated component; a GLOBAL rule with surviving consumers RELOCATES to legacy-globals.scss (ADR-005), and the migrated element DROPS that legacy class hook so the relocated rule's element-level sub-selectors (e.g. `#complianz .cmplz-error-text p` = (1,1,1)) can't override the migrated tw- styling (tw- utilities are only (1,1,0)). (2) Reproduce a one-shot/transient CSS animation as a `@keyframes` (for an unmarked row, put it in page.css with LITERAL colours — tokens are island-scoped) or reset the driving state; never as a static token background on a flag that is only ever set. (3) A light accent tint cannot carry accent-strong text at AA — add a dedicated darker on-tint token (`--cmplz-accent-on-subtle` #17608f, ~5.9:1) for interactive text/icons on `--cmplz-accent-subtle`; and when proposing tints, run the contrast for INTERACTIVE text on them, not just body text, before sign-off.
promote-at: 0.8 -> a checklist line in the Phase-4 section-migration guidance (global-rule relocation + hook-drop; transient-animation reproduction; interactive-text-on-tint AA) and a note in the token design-note template

### 2026-10-13 frame/body migration: dead-rule greps, in-card overlay stacking, and responsive variant direction
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-046 (Phase-4 section 1b, the settings-screen frame) — the pre-push adversarial review confirmed 11 findings (4 distinct), three of them generalizable to every remaining Phase-4 section. (1) ADR-005 DEAD-RULE false positive: `.cmplz-grid-item.no-background` was deleted as "dead, no JS consumer (grep-verified)" but a JS-scoped grep over settings/src missed that the class literal lives in PHP — settings/config/blocks.php sets `'class' => '... no-background'` for the dashboard `other-plugins` block, rendered by the still-legacy GridBlock.js. Deleting it un-suppressed the base `.cmplz-grid-item` card chrome on that block. (2) IN-CARD OVERLAY STACKING: the premium-lock scrim used `tw-z-[var(--cmplz-z-overlay,30)]` on `.cmplz-locked`, but its card was only `tw-relative` (z-auto, NOT a stacking context), so the scrim's z-30 leaked to the body context and painted over + click-blocked the sticky footer (`--cmplz-z-sticky` 20) — inverting the legacy footer(12)>lock(10) order. (3) RESPONSIVE VARIANT DIRECTION: the body used `tw-col-span-1 md:tw-col-span-2`; because the project's Tailwind screens are min-width and `md`=1080px, the BASE (`col-span-1`) applies BELOW 1080 and `md:` only at/above — the exact inverse of the legacy `@media(max-width:1080){span 4}` (full width when narrow), collapsing the body to a ~1/4 sliver on tablets/narrow windows.
action: (1) Before deleting a legacy SCSS rule under ADR-005, grep ALL consumers, not just settings/src JS: PHP (settings/config/*.php, especially blocks.php class strings), e2e specs, and dynamic className suffixes (e.g. `cmplz-<id>`, `cmplz-<label>`). A class can be configured in PHP and only rendered via a generic JS mapper. When in doubt, RELOCATE to legacy-globals and defer deletion to the section that owns the last consumer. (2) When migrating a container that holds an absolutely-positioned in-card overlay (lock scrim, popover) AND coexists with a global sticky/fixed element, give the card `tw-isolate` (isolation:isolate) so the overlay's z stays contained — otherwise a `position:relative; z-auto` card is NOT a stacking context and the overlay's z competes app-wide. (3) To reproduce a legacy `@media(max-width: BP)` collapse with Tailwind's min-width variants, the BASE utility must be the NARROW/below-BP value and the `md:`/`lg:` variant the wide value (invert the mental model). Verify by reading the <BP (e.g. 768px) baseline, not just 1440px — the e2e shoots 768 + 1440, so a narrow regression IS captured but is easy to misread at desktop width.
promote-at: 0.8 -> a checklist line in the Phase-4 section-migration guidance (all-consumer grep incl. PHP/config; isolate in-card overlays; invert responsive variant direction) + a note in ADR-005

### 2026-10-13 a migrated tw- display utility defeats a retained `:empty{display:none}`; test the discriminating order
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-048 (Phase-4 Dashboard). Two generalizable misses the adversarial review caught. (1) EMPTY-FOOTER SHELF: GridBlock renders a footer `<div className="cmplz-grid-item-footer <footerCls>">` whenever the block config declares a footer, even when the footer React component returns null (ToolsFooter) — so the div is `:empty`. The retained shared base `:where(.cmplz) .cmplz-grid-item-footer:empty { display:none }` (0,2,0) used to hide it, but the migrated `footerCls` starts with `tw-flex`, which the `important: :is(#complianz,#complianz-portal)` config boosts to (1,1,0) — an ID beats any number of classes, so `display:flex` won and an empty ~24px shelf rendered. (2) VACUOUS PRECEDENCE TEST: the only variant-conflict test fed `'border-to-border no-background'`, where the unconditional borderless assignment runs last — so it passed even if the border-to-border precedence guard were deleted; the discriminating order `'no-background border-to-border'` (borderless must NOT be downgraded) was untested.
action: (1) When migrating a container/footer/section that (a) is conditionally rendered as a wrapper around an optionally-null React child and (b) relied on a RETAINED legacy `:empty{display:none}` (or similar) base rule, add the matching tw- `empty:` variant to the migrated element (e.g. `empty:tw-hidden` → `:is(#id) .empty\:tw-hidden:empty{display:none}` at (1,2,0), which beats a bare `tw-flex` at (1,1,0)). More broadly: whenever you give a migrated element a tw- `display`/layout utility, check whether a retained legacy rule set `display` on it conditionally (`:empty`, `:not()`, state classes) and reproduce that condition as a tw- variant, because the important:-boosted utility will otherwise win unconditionally. (2) For any precedence/conflict/first-wins logic, write the test with the input ORDER that forces the guard to discriminate (the order where the naive/unguarded code gives the WRONG answer), not just an order that passes either way — otherwise the test is vacuous and a future regression ships green.
promote-at: 0.8 -> a checklist line in the Phase-4 section-migration guidance (reproduce retained conditional-display rules as tw- variants; test the discriminating order for precedence logic)

### 2026-10-14 the token-hygiene gate greps the WHOLE file (comments too) — vendor/preview CSS must use literals, not legacy var names
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-050 (Consent banner). ADR-008 §26 says vendors/preview.css should pin the isolate-zone typography as "commented literals of the legacy .cmplz values", wording that implies keeping the legacy var NAMES (--cmplz-legacy-fs-300, --cmplz-legacy-text-color) in /* comments */. But the token-hygiene CI gate (checks.yml) greps the ENTIRE file tree under settings/src AND settings/src/styles for `--cmplz-legacy-`/`--rsp-` — it does NOT skip comments. So writing those names even inside a comment FAILS the gate. The implementer resolved the vars to concrete literals (0.8125rem, rgba(15,23,42,0.95)) and cited base.scss line-refs + prose ("legacy fs-300 / text-colour variable") instead of the var-name strings — faithful to the ADR's "commented literals" INTENT, and matching the tokens.css T-020 precedent (which also avoided the --cmplz-legacy- string entirely). The adversarial review confirmed zero --cmplz-legacy-/--rsp- in preview.css.
action: In any hand-authored CSS under settings/src/styles (vendors/preview.css now; the ADR-009 vendor files — date-range/toastify/shepherd/data-table overrides — coming in the tables + statistics/date-range sections), NEVER write a `--cmplz-legacy-*` or `--rsp-*` token NAME, not even in a comment. Pin the concrete literal VALUE and cite the source as a file:line ref + plain-English name ("the legacy fs-300 / text-colour variable"). When an ADR's wording says "keep the legacy var names in comments", treat the token-hygiene gate as overriding it (the gate is a hard CI check; the literal + line-ref preserves traceability). Underscore-form frontend-banner vars (--cmplz_banner_width etc.) are NOT matched by the dash-form grep and are safe to keep verbatim.
promote-at: 0.8 -> a note in ADR-008/ADR-009 + the token-hygiene gate docs (vendor CSS uses literals + line-refs, never legacy var-name strings even in comments)

### 2026-10-14 a Button/primitive in MARKERLESS chrome renders borderless (B1 scope); verify a suspicious baseline against the live DOM before chasing a code bug
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-052 (Phase-4 Integrations). Two generalizable lessons. (1) MARKERLESS-BUTTON-BORDER: the `ui/Button` primitive draws its edge with `tw-border` (border-WIDTH only) + `tw-border-[<color>]`; its border-STYLE comes solely from base.css B1 (`:is(#complianz,#complianz-portal) :where([data-cmplz-ui] *){border-style:solid}`), because Preflight is off (ADR-014). The migrated "Add new"/URL buttons were placed in bare markerless `<div>` wrappers (the Script Center body carries no marker — it hosts the still-legacy Panel accordion), so B1 never reached them: border-width:1px + border-style:none → a borderless blue-text "link", NOT the approved bordered `secondary` button. (The Save/Delete row was fine — I had marked it `data-cmplz-ui` so the `error` variant's unfallbacked `var(--cmplz-danger)` would resolve, which incidentally also gave B1's border-style.) The consent-banner's markerless Button worked only because it renders inside the Menu island (`data-cmplz-ui` on the Menu root). The 5-dimension adversarial code review MISSED this (it reasoned about token resolution + specificity, not Preflight-off border-style); the visual RE-BASELINE caught it. (2) VERIFY-BASELINE-vs-LIVE: once fixed, the full `npm run e2e` visual suite STILL captured the button borderless across 3 runs — but the live app (:8888 and :8889, computed `border-style: solid`) and three standalone Playwright probes (single-screen, multi-screen, element-screenshot) all rendered the border correctly. It is a raster artifact of the heavy full serial suite on the NON-BLOCKING visual layer (only one `index.*.js` on disk, marker present, computed style solid at capture time — so not a stale bundle, re-seed, or accumulated state).
action: (1) When placing a `ui/Button` (or any primitive whose border-style relies on base.css B1) in MARKERLESS chrome, ensure a `data-cmplz-ui` ancestor is in scope — mark the pure-primitive wrapper (one that hosts only migrated primitives, never a legacy accordion/table/body), exactly as the Save/Delete row and the consent-banner Menu island do. Remember the `error` variant additionally needs the marker (or a literal fallback) to resolve `var(--cmplz-danger)`/`var(--cmplz-text-on-accent)`; literal-color variants (secondary/tertiary/primary) resolve markerless but STILL lose their border without it. Add "button renders bordered in a markerless subtree?" to the body-migration checklist, and have the adversarial review check border-STYLE under Preflight-off, not just token resolution. (2) When a re-baseline shows a migrated element looking wrong, VERIFY against the live DOM first (computed style + a focused element screenshot / a standalone Playwright probe) before assuming the code is broken — the full visual suite can drop a fine detail (a 1px border) under load that the live app and single-screen captures render correctly. The canonical harness baseline is self-consistent with CI (same harness/load), so commit the harness output rather than a hand-generated screenshot (which risks a permanent method-mismatch diff on every future re-baseline); document the live-vs-harness delta in the task outcome.
promote-at: 0.8 -> a checklist line in the Phase-4 section-migration guidance (mark the wrapper for Buttons in markerless chrome; review border-style under Preflight-off) + a note in ADR-001/ADR-013 and the baselines doc (verify a suspicious baseline against the live DOM; commit canonical-harness output)

### 2026-10-16 data-tables: constant full-bleed, axe-gating surfaces shared-chrome contrast, the styled-components vendor is the trivial case, and wp-env multi-instance ops
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: T-054 (Phase-4 data-tables; the react-data-table owner, ADR-009 Option B). Four generalizable lessons, three caught by the pre-push adversarial review + the axe gate, one by the e2e infra. (1) FULL-BLEED MUST BE CONSTANT when the migrated field-wrap padding is constant: Field.js pads the field-wrap a flat tw-px-[space-l]=24px (no responsive variant), so edge-to-edge = margin-inline:-24px at EVERY width. I mechanically ported the legacy datatables.scss's breakpoint-STEPPED negative margins (-25/-20/-15px at 1280/960) — but those only worked because the legacy CONTAINER padding was itself responsive; against constant 24px padding the steps reintroduce an 8-12px inset below 1280px (incl. the 768 e2e snapshot), the exact seam the port was meant to close. Also a stray 960px step matched no project breakpoint (768/1080/1280). (2) ADDING A SCREEN TO axe MIGRATED_SCREENS SURFACES PRE-EXISTING serious/critical on the SHARED chrome it renders: gating #integrations/integrations-services failed on a color-contrast the Help-notice callout (Help.js, shared, from 1b) always had — its "More info" link was --cmplz-accent-strong (#1e73be) on the --cmplz-accent-subtle (#e3f2ff) tint = 4.33:1 < AA (the SAME T-045 pairing). The help sidebar is MASKED in visual.spec, so ONLY the axe layer catches it; the fix is the T-045 token --cmplz-accent-on-subtle (#17608f, ~5.9:1, AA on both the accent-subtle and warning tints), which is masked so it costs zero baseline churn. (3) A styled-components vendor (react-data-table) is the TRIVIAL vendor case: no importable upstream stylesheet, CSS-expressible via the stable .rdt_* classes, rendered in the MARKERLESS field-wrap — so it needs only a hand-authored, scoped, logical, token-LITERAL overrides file (the preview.css pattern), NOT the ADR-009 postcss auto-scope step, NOT readToken()/createTheme, and NOT a data-cmplz-isolate zone (an isolate zone would strip the self-marked in-cell SwitchInput/CheckboxGroup primitives of the base reset — the markerless-Button lesson again). The heavy ADR-009 machinery is for vendors WITH upstream CSS (react-date-range) or JS canvas colors (chart.js) — defer it to its first real consumer. (4) An aria-label built from a WRONG/absent prop (service.name, when the services payload only has id/label/source/placeholder) still PASSES axe button-name (non-empty: "Enable ") but silently defeats the per-row-name intent — grep the payload shape; the sibling PluginsControl correctly used plugin.label. INFRA: an e2e after a multi-day gap failed at waitForAppMounted because a FOREIGN wp-env instance (wp-env-e2e-<hash>, started by the playwright webServer from tests/e2e) squatted :8888 while the root instance was stopped, so the webServer reused the foreign one but the setup's `wp-env run cli` (root cwd) hit the stopped root -> "service cli is not running"; --no-deps compounded it (stale 2-day auth never refreshed -> logged-out 403 -> app never mounts).
action: (1) When porting a vendor/full-bleed negative-margin from legacy SCSS, CHECK whether the legacy value was responsive BECAUSE the legacy container padding was responsive; if the MIGRATED padding is a constant token, the negative margin must be the matching CONSTANT (one -space-l, no @media). Drop breakpoint steps that no longer have a responsive counterpart, and never carry a breakpoint value that matches no project screen. (2) Before adding a screen to MIGRATED_SCREENS, expect the BLOCKING axe gate to surface serious/critical on SHARED chrome that screen renders (help notices, callouts, tooltips) that the visual layer masks and so never flagged — run a scoped axe pass or reason about every shared component on the screen; fix interactive-text-on-tint with --cmplz-accent-on-subtle (the masked fix is baseline-free). (3) For a styled-components vendor with no upstream CSS, land ONLY a scoped token-literal overrides file (preview.css pattern) + behavior; do NOT build the postcss auto-scope step, readToken(), createTheme, or an isolate zone until the first consumer that actually needs them (react-date-range / chart.js). (4) When adding an aria-label from a data field, confirm the field EXISTS on the payload (grep the REST shape / the PHP that emits it), not just that it compiles; a non-empty-but-constant label passes axe while failing the a11y intent. INFRA: verify e2e on a freed :8888 with the ROOT wp-env instance up (`npx wp-env run cli wp option get siteurl` must work) and run WITH the setup project (not --no-deps) after any multi-day gap or container restart, so the DB is reseeded and auth refreshed.
promote-at: 0.8 -> checklist lines in the Phase-4 section-migration guidance (constant full-bleed vs responsive-padding; axe-gating surfaces masked shared-chrome contrast; aria-label field-exists check) + a note in ADR-009 (styled-components vendor = overrides-only, no auto-scope/isolate/readToken until the first real consumer) + a conventions "Gate" note (run e2e WITH setup on a healthy root wp-env instance after a gap)
