# Learnings

Lessons and scored instincts captured by `/flow:learn` and `/flow:retro`.

### 2026-10-06 flow gate hook matches the command text, not what actually runs
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: The PreToolUse gate (flow `scripts/gate.js`) regex-matches the raw Bash command string. During `/flow:init`, a self-test whose JSON payload merely contained `git commit --no-verify` inside quotes was blocked before anything ran. The commit regex (`\bgit(\s+\S+)*\s+commit\b`) also spans chained commands, so any command with `git …` followed later by a space-separated `commit` or `push` word triggers the full check run first.
action: Keep the words `git … commit` / `git … push` and the skip-hooks flag out of any Bash command that is not a real commit or push. Put such text (test payloads, snippets) in a file with the Write tool and reference the file instead.
promote-at: 0.8 -> becomes a CLAUDE.md line, or a gate.js fix proposed upstream via `/flow:retro` (match executed commands, not quoted text)

### 2026-10-07 don't set a verification bar that normal e2e flake can't clear
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: For T-010 (visual/isolation screenshot baselines) the dispatcher demanded "5x double-proof all green + repeat-each + throttle" — 12+ cold runs, each perfect. Against a suite with ~1/10 residual flake (a login-cookie race + one banner screen at 768px), any single flake fails the campaign, so the implementer looped regenerate->fail->restart for ~4.5h without converging. The plan's own policy (§8.1.4) was the right bar all along: green with CI retries (`retries: 2`), anything that only passes on retry flagged flaky. After taking over, fixing the real login race (retry + nav wait) and seeding the documents the banner preview needs, the suite went 3x clean with retries unused.
action: When accepting an inherently flaky e2e/screenshot suite, use the project's retry policy (green with retries, flaky flagged) as the bar, not "N cold runs all green". Fix the identifiable root-cause flakes (races, missing deterministic state) directly; let retries absorb irreducible transient flake. Watch for an agent thrashing (repeated full re-runs, same ~1 failure each pass) as the signal the bar is wrong, and intervene rather than wait.
promote-at: 0.8 -> becomes a line in the planning or tdd skill: proof commands for flaky suites specify the retry policy, never a perfect-cold-run count

### 2026-10-08 verify e2e on a RESET db, one pass per task
confidence: 0.5   # raised: the "same-DB, many runs" habit hid a real CI-blocking bug AND burned hours
context: The screenshot baselines (T-010) and a page-rules assertion passed every verification for three tasks (T-010, T-011, T-032) but only because every run reused the same ACCUMULATED wp-env DB. A `npx wp-env reset` (fresh DB = the real CI condition) exposed that the seed does not pin Complianz's notices/notifications, so those screens/assertions were non-reproducible and would have failed in CI. Separately, running two or three full fresh-DB verifications per task (each ~15 min: reset → reseed → build → suite) turned the baseline work into hours the maintainer pushed back on.
action: Verify e2e work on a RESET database (`npx wp-env reset` first), never the accumulated one — "passes locally" must equal "passes in CI". And run ONE fresh-DB verification pass per task, not a stack of them; trust the agent's own logged fresh-DB runs plus a read of the raw log over re-running. Accept flaky-then-passes under the agreed `--retries=2` policy; don't open a determinism hunt for every retry-absorbed flake.
promote-at: 0.8 -> a line in conventions.md "Gate"/testing section and the flow planning skill (e2e proofs reset the DB; one verify pass)

### 2026-10-10 don't key CSS tokens to a DOM element a later phase will create
confidence: 0.3   # 0.3 first observation, +0.2 each recurrence, cap 1.0
context: tokens.css (T-020) declared the `--cmplz-*` semantic tokens ONLY on `#complianz-app-root[data-cmplz-ui], #complianz-portal-root[data-cmplz-ui]`, but `#complianz-app-root` is not rendered until the Phase-5 marker move (ADR-001) — the app mounts into `#complianz-app` and Page.js's root is `.cmplz-wrapper`, neither carrying the id/marker. The portal root DOES exist, so portal content (dialogs/popovers/combobox menu) was fine, masking the gap. Every MAIN-APP primitive consumer (T-026 Support textarea, T-027 combobox control, T-028's 7 inputs) therefore resolved every `var(--cmplz-*)` to invalid-at-computed-value-time -> token-less render (dark currentColor border, 0 radius, 0 inline padding, no focus ring). It slipped three tasks because the primitives were unused until T-026+, functional e2e doesn't assert styling, and visual.spec is non-blocking (Option B) against stale baselines, so the drift never hard-failed; the T-028 implementer misread the 26-screen drift as a minor text-color shift. The adversarial review surfaced it but the verify step wrongly dismissed it as "accepted Phase-2 state" (it misread ADR-001's deferral of the marker MOVE as a deferral of working tokens). Caught by manually confirming the CSS source + fresh build + reading the visual.spec actual.png (a dark square NumberInput).
action: Scope design tokens to the SAME selector model as the scoped base (base.css targets `[data-cmplz-ui] *`; tokens now declare on `:is(#complianz,#complianz-portal) :where([data-cmplz-ui])`) so they reach every migrated island in the phase they are consumed, not a root element a future phase introduces. When a token/base layer and its consumers land in different tasks, VISUALLY verify one real consumer renders look-preserving in the running app (read the screenshot), don't trust functional-green + non-blocking visual drift. And when an adversarial-review verify step dismisses a finding as "accepted/known", re-check the primary evidence before trusting it.
promote-at: 0.8 -> a line in ADR-001/ADR-014 (token scope = island model until Phase 5) and the conventions "look-preserving means verify a rendered consumer" note
